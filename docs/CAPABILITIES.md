# Role-specific capabilities

This release covers all **167 public distributions**: 114 Agency, 30 Academy, 22 Council, and standalone Wear. It adds 25 reviewed skill trees across 243 role-specific assignments, plus an on-demand capability guide in every distribution. The complete [matrix](CAPABILITY_MATRIX.md) records every profile, including deliberate retain-only decisions.

## What installs by default

- Existing SOULs, original skills, preloads, teaching/coaching contracts and tool restrictions are preserved. Release metadata versions advance; no identity is renamed.
- Selected skills, their reference documents, scripts, templates and license notices ship with the profile. They are available **on demand**, not blanket-preloaded. Inclusion does not install dependencies or authorize tool execution.
- Six plugins are offered where relevant: RFC, OSV, GitHub, PEP and Wikipedia context references, and optional Snyk. They are pinned declarations, **not downloaded or enabled by profile installation**.
- Thirteen remote MCP integrations have role-specific **disabled** native config templates: Context7, DeepWiki, AWS Knowledge, Microsoft Learn, Sentry, Grafana Cloud, Linear, Wolfram, Kiwi, trivago, AllTrails, Strava and Todoist. Agency Pixel Artist also ships two disabled local stdio templates for Pixelorama and Aseprite. There are 73 per-profile MCP selections. Newly introduced config seeds contain no model/provider choices, credentials or enabled remote connection.
- Wear and coordination-only profiles receive a discovery guide, not a general execution bundle or external integration.

A normal profile distribution remains the supported installation/update mechanism; this repository adds no runtime installer, scheduler, memory service, orchestration system or automatic account connection.[1]

## Skill ownership and deduplication

`capabilities/profiles.json` is the exact selection authority. `capabilities/skills.lock.json` records public repository commits, original file hashes, adapted file hashes, licenses and installation paths. `capabilities/skills/` is the canonical reviewed source; `capabilities.py --write` materializes portable copies offline. `--check` verifies every generated byte, exact roster coverage and safety decisions.

Bundled additions use their native Hermes category paths, so first-start seeding does not create conflicting copies. Optional/community additions live under `skills/capabilities/`. The existing top-level role-owned `jobs` contract stays unchanged; Agency catalog output adds `supplemental_capabilities` as a separate, additive field.

Three pre-existing profile skills overlap Hermes bundle names: Editor-in-Chief's `humanizer`, Market Researcher's `grounded-citations`, and Systems Architect's `architecture-diagram`. Byte-identical copies of those original profile-owned trees occupy the corresponding native bundle destination. Hermes deduplicates identical same-root copies, and seeding preserves the authored content. These are compatibility shadows, not extra effective capabilities. Their exact bytes are checked, including after repeated native seeding.

Hermes bundled seeding, same-name ownership and progressive disclosure must be considered together: a file absent from a source distribution is not necessarily absent after startup.[2]

Original source hashes are captured in `capabilities/baseline.json` as this release's preservation fence. An intentional future change to an original skill must update that baseline explicitly after review, not bypass validation.

## Optional integrations and privacy

Each installed `profile-capabilities` skill carries `references/catalog.json`: exact choices, reasons, immutable plugin pins, prerequisites, provider disclosures and individual disabled-install command arrays. A list entry does not mean a service is configured, authenticated or operational.

**No implicit activation:** normal pack installation does not call plugin installation, MCP catalog installation, OAuth, package managers or remote tools. The editor templates require explicit, pinned source builds with the shipped patches. The Pixel Asset Export skill documents workstation setup and smoke checks. Fresh profile seeds set `enabled: false`; MCP sampling and elicitation are disabled, resources/prompts are disabled, and exact tool allowlists prevent future vendor tools from automatically becoming available. Account-backed integrations start with `tools.include: []` until authenticated schemas and user scopes are reviewed. That empty list means deny all, not allow all.[3]

**Critical native behavior:** `hermes plugins pack install` is an explicit activation operation and enables successful installs. The packaged `references/hermes-pack.yaml` files are pinned opt-in activation recipes, not disabled staging. To stage one chosen plugin, use its catalog command ending in `--no-enable --no-deps`, inspect the real declared capabilities/dependencies, then separately approve activation. Plugin catalog review and a commit pin do not certify downloaded dependency trees or hosted service behavior.[4]

Before activation:

1. Verify exact profile, existing connectors, same-name server/plugin conflicts and current CLI help. Prefer an existing equivalent connector/native tool; do not connect two overlapping systems.
2. Obtain consent for the named service, data disclosure, permissions, downloads, costs and intended action. Anonymous does not mean private: queries, locations, public repository identifiers and client IPs still leave the machine.
3. Use supported Hermes UI/CLI and protected authentication. Never paste secrets into chat, copy credentials between profiles, disable TLS or hand-edit live configuration.
4. Review tool scopes and exact allowlists. Preserve exclusions such as AWS skill retrieval, Wolfram automatic context upload, Kiwi feedback, and Grafana assistant/agent orchestration tools.
5. Read back enabled state and discovered tools, test a non-sensitive read, and state reload/new-session requirements. Never restart a gateway implicitly. Missing auth/network/dependencies mean unavailable, not fabricated success.

Special disclosures:

- **Snyk:** source/dependency-graph uploads need separate per-project consent. CLI credentials may live outside Hermes; profile-isolated credential handling is not established by the wrapper. Do not activate until that boundary is reviewed. Native Hermes `security` remains the default dependency-audit option.
- **Grafana:** the selected endpoint is Grafana Cloud, not self-hosted Grafana. Connection can count as a billed Assistant user. Start with minimal read permissions.
- **Strava:** subscription/OAuth and sensitive health/location disclosure require explicit consent.
- **Wikipedia:** autocomplete prefixes are sent before message submission. Never type sensitive information after its reference prefix.
- **AllTrails:** large schemas; enable only needed tools, use coarse location and do not treat route/weather output as a safety guarantee.
- **Excalidraw:** local JSON generation is account-free. Uploading a diagram for a share link is a separate data-disclosure decision.

## Deliberate exclusions

This is a completed selection, not a deferred rollout wave. `capabilities/research.json` preserves bounded Hub discovery evidence and rejection reasons; `capabilities/integrations.json` records integration decisions.

- Figma/Indeed are not promoted because current client-approval/support restrictions are unresolved for Hermes. No client-identity disguise is authorized.
- Atlassian is not promoted because the catalog endpoint and current vendor endpoint/version policy differ; no silent URL migration.
- Blender's reviewed wrapper was not promoted: auto-launch/online-mode and a persistent unauthenticated local Python bridge need a separate application-specific decision. Existing art/scene workflows remain intact.
- Jupyter's unauthenticated-server/XSRF-disabling instructions and global helper checkout are rejected. Native `execute_code` already offers persistent state.
- Memento's skill-tree persistence/global locations, Impeccable's catalog-only stub/floating executable download, and HyperFrames' global/floating setup are not default additions.
- Generic coaching/persona bundles, broad filesystem/shell MCPs, additional orchestrators, automatic publishers and payment/booking integrations add duplication or risk rather than a necessary capability.

Hub discovery spans 26 domain queries, with up to six results each; search rank is not a quality certification or a claim of exhaustive coverage of every registry entry. Full selected trees and official/native alternatives determine promotion, not popularity.

## Updating and rollback

Use the normal repository selector and Hermes profile distribution installation/update path. To inspect a profile's choices, load `profile-capabilities`, then its catalog reference. New installations receive disabled MCP seeds; **updates preserve existing config by default**, so a new seed does not silently reset existing accounts or user settings.[1]

Native updates replace shipped skill roots, including user edits inside those roots; they preserve separately added skill roots. Review collisions before updating. This upgrade does not promise to merge user-edited shipped skills automatically. Existing live profiles, plugins, accounts, memories and gateways were not changed during development.

Source rollback is a reviewed revert to the prior public revision. Installed rollback is a separate approved operation: restore prior explicit config/enabled state through supported interfaces, retain credentials and user-owned data, and remove only positively identified upgrade-owned additions after review. Updating an older distribution alone does not guarantee removal of roots the old distribution no longer ships.

## Verification

Run static/source checks:

```bash
python capabilities.py --check
python validate.py
python -m unittest discover -s tests -p 'test_*.py'
python -m unittest discover -s hermes-agency/tests -p 'test_*.py'
python -m unittest discover -s hermes-council/tests -p 'test_*.py'
python -m unittest discover -s hermes-academy/tests -p 'test_*.py'
```

For the native install/seeding/discovery/update proof, use an authorized Hermes source interpreter and a disposable scratch directory on the build/test machine:

```bash
python scripts/verify_native_capabilities.py --hermes-source /path/to/hermes-agent --scratch /path/to/disposable-scratch
```

The proof blocks network connections, installs all exact profiles into a temporary home, verifies every shipped skill/support byte before and after repeated seeding, checks discovery, parses native plugin packs, and exercises config/user-skill preservation and existing-profile refusal. It does not activate account integrations or certify model behavior.

See [CAPABILITY_VALIDATION.md](CAPABILITY_VALIDATION.md) for actual results, dependency boundaries and the optional LibreOffice limitation. Tested Hermes source: `557254faa24ef5d86f67595c4c64dc61644d0f68` (reported CLI version `0.22.5+3257.g557254f`). No claim is made that every earlier Hermes release supports these contracts. Continuing Education's separately documented compatibility boundary remains unchanged.
