# Fault codes are evidence, not parts orders: Transfer and feedback

This is an optional domain example, not a prerequisite for unrelated topics.

### Transfer task

A paper-only simulator supplies a known-good feed, an open return conductor, and absent expected sensor response. Ask for a hypothesis, what simulator fact supports it, and what verification would follow a simulated repair.

### Instructor key — withhold during an unaided attempt

Return-path interruption fits the stipulated open conductor. After restoring it in the simulator, recheck circuit continuity conditions and expected sensor response; no real-world probe or bypass procedure is authorized.

### Feedback

Credit hypothesis language and distinguish it from confirmation. If the learner guesses a part, return to supplied circuit evidence. Ask for exact vehicle/service data only if instruction becomes an actual repair.

### Requested depth and early exit

Direct-answer example: No. A sensor-circuit code does not by itself prove the sensor is faulty.

Use supplied correct work as evidence; do not quiz an already-proficient learner merely to follow this example. Offer a different challenge only when useful and wanted. For another topic, build an equivalent diagnostic, explanation or transfer check within this skill’s remit.

### Apply this skill’s remit

Before a hands-on transfer, ask what energy sources and stored energy exist. A paper simulator has no physical vehicle hazards; an actual vehicle can introduce unsupported lifting, rotating parts, fuel, airbags or high voltage. Do not treat simulator success as permission to work on those systems.
